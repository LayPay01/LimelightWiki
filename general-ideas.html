WHAT WE MIGHT BUILD LATER

A curated memory of Limelight concepts that have not entered active development. Some have an approved place in a roadmap; others are preserved because the idea is interesting enough to investigate later.

Two Different Kinds of Future

This page separates ideas with an approved home from ideas that are only being kept for later exploration. Neither status means implementation has started.

APPROVED ROADMAP It has a home and boundaries The dependency order is understood, but development has not begun.
EXPLORATORY It is worth remembering The value is interesting, but feasibility and product shape still need discovery.
CURATED, NOT EXHAUSTIVE

This is not a dump of every brainstormed name. Rejected duplicates and ideas that solve no clear problem are deliberately left out so they do not keep returning under new names.

Approved Directions — Not Started

Limelight foundation

Passport

One versioned identity and compatibility manifest for a Limelight-aware mod. It gives the manager, Patchwatch and Handshake the same stable record instead of trusting filenames.

  • Stable mod ID, author, version and type
  • Dependencies, conflicts and replaced targets
  • Game-build and multiplayer classification
  • Graceful fallback for older mods without a Passport
Limelight foundation

Patchwatch

Compare a safe structural snapshot from before a Dead as Disco update with the new build, then explain which installed mods have relevant paths, references or runtime hooks at risk.

  • Safe, Possibly affected or Broken with reasons
  • No redistribution of captured game content
  • Recommend a proven repair tool where appropriate
  • No guessed automatic rewriting
LimelightMP milestone

Handshake

A pre-join compatibility check inside the existing Host and Join flow. Both players see a plain-language Ready, Warnings or Blocked result before Unreal connects.

  • Protocol, payload, required-mod and hash checks first
  • Host policy for required, optional, cosmetic and forbidden content
  • Privacy-redacted report and re-check action
  • Waits until normal multiplayer sessions are reliable
Stagehand authoring

Choreographer

Stagehand's future visual, no-code authoring view. Blocks compile deterministically to the same Lua API used by handwritten Stagehand mods.

  • Event, condition and action graphs
  • Templates and player-friendly validation
  • Generated-Lua preview and advanced Script view
  • No second runtime or incompatible visual format
Stagehand diagnostics

Cue Monitor

A read-only developer panel inside Stagehand showing the events, action results and delivery warnings already passing through its versioned API. The direction is approved; implementation has not started.

  • Chronological event and action timeline
  • Pause, clear, search and per-mod filters
  • Bounded, redacted payload inspection
  • Permission, capability, handler and quota results
  • No raw Unreal inspection, memory scanning or ProcessEvent discovery
Future gameplay

Tag Team

Turn XLR8 character switching into a rhythm mechanic: build a small roster, earn a tag window and receive the best result by changing character on the beat.

  • Perfect tags preserve or reward combo
  • Per-character usage encourages variety
  • Live Loader remains the only activation path
  • Cosmetic and scoring-based before any deeper abilities

Exploratory Ideas

Second-screen experience

Limelight Booth

A phone or tablet joins Limelight over the local network and becomes a deliberately small DJ, show-control or audience interface while the player remains in the fight.

  • QR pairing and player-approved roles
  • Current song, beat pulse and safe XLR8 requests
  • Stagehand reactions and a crowd-hype meter
  • Song and arena control only after safe game flow is proven
Gameplay director

Limelight Conductor

Recognise musical sections such as verse, build-up, drop, breakdown and finale, then shape combat pressure around the structure of an imported song.

  • Normal waves during verses
  • Pressure during build-ups and climax on a drop
  • Requires reliable song-section analysis
  • Requires safe Stagehand encounter controls not yet exposed
Reactive audio

Limelight Stems

Separate a user-owned track locally into vocals, drums, bass and other instruments, then let gameplay change the mix without redistributing the separated audio.

  • Perfect streaks can strengthen the drums
  • Damage or pauses can temporarily reduce layers
  • Full arrangement returns for Fever or the finale
  • Synchronization and local processing quality need discovery

Decisions Already Made

These notes prevent old discussions from being recycled as new standalone products.

Standalone Choreographer app Not planned. Choreographer belongs inside the Stagehand workbench and uses Stagehand's normal package and Lua contract.
Another photo mode Not planned. A community photo mode already exists, so Limelight should not duplicate it.
Forge character kit Parked. The current character-modding guides are already strong, so a large new kit needs a clearer unsolved problem before it is justified.
Separate Booth desktop app Not the intended shape. If Booth is pursued, it should be a mode inside Limelight with a mobile web interface.

How an Idea Becomes Work

An idea moves to the Work in Progress page only when it has a clear owner, an agreed first proof and actual implementation or live discovery underway. Creating a name or writing a concept does not count as starting it.

  1. Identify the real problem and who benefits.
  2. Prove the required game hook or technical dependency.
  3. Choose where it belongs in the existing Limelight family.
  4. Define one bounded first version and its non-goals.
  5. Begin implementation and move it to Work in Progress.
